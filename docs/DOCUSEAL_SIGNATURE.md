# Signature électronique — DocuSeal auto-hébergé

> Remplace Yousign depuis septembre 2026.
> Yousign reste **fonctionnel et réactivable** : `SIGNATURE_PROVIDER=yousign`.

Instance : <https://sign.globalafricaplus.com> (Docker, catalogue Hostinger, v3.2.3)
Docs API : <https://www.docuseal.com/docs/api>

---

## 1. Pourquoi DocuSeal

| | Yousign | DocuSeal auto-hébergé |
|---|---|---|
| Coût | par signature | **0 €** (serveur déjà payé) |
| Données | hébergées chez l'éditeur | **sur notre VPS** |
| Volume | plafonné par le forfait | illimité |
| Valeur juridique | eIDAS avancé possible | signature simple + piste d'audit |

⚠️ Le certificat par défaut est **auto-généré** (« DocuSeal Self-Host
Autogenerated »). Pour une opposabilité maximale, téléverser un certificat
qualifié dans *Paramètres → E-Signature* et renseigner une URL de serveur
d'horodatage (TSA).

## 2. Architecture

| Élément | Fichier |
|---|---|
| Prestataire actif | `config/signature.php` (`SIGNATURE_PROVIDER`) |
| Réglages DocuSeal | `config/docuseal.php` |
| Client HTTP | `app/Services/Convention/DocuSealClient.php` |
| Contrat commun | `app/Services/Convention/Signature/SignatureProviderInterface.php` |
| Implémentations | `Signature/DocuSealProvider.php`, `Signature/YousignProvider.php` |
| Orchestration | `app/Services/Convention/ConventionSignatureService.php` |
| Webhook | `POST /api/v1/webhooks/docuseal` |
| Diagnostic | `php artisan docuseal:check [--investment=ID]` |

Le prestataire retenu est **mémorisé sur chaque investissement**
(`investments.signature_provider`) : une convention envoyée chez Yousign avant
la bascule continue d'être suivie chez Yousign.

### Flux

```
paiement confirmé
   → ConventionGenerator : .docx (modèle selon le type) → PDF (LibreOffice)
   → DocuSealProvider    : POST /api/submissions        (mode « template »)
                        ou POST /api/submissions/pdf    (mode « oneoff », Pro)
   → DocuSeal            : 2 signataires (Investisseur, Porteur de projet)
   → webhook form.completed / submission.completed
   → syncStatus()        : GET /submissions/{id} puis
                           GET /submissions/{id}/documents?merge=true
   → PDF signé stocké, contract_status = "signed"
```

### Deux modes — `DOCUSEAL_MODE`

L'édition **libre** auto-hébergée verrouille toute création de document par API.
Sondé sur l'instance le 2026-09-05 :

| Endpoint | Édition libre |
|---|---|
| `POST /submissions` (depuis un gabarit) | ✅ |
| `POST /templates/{id}/clone` | ✅ |
| `GET /submissions/{id}` · `/documents` | ✅ |
| `POST /templates/pdf` · `docx` · `html` | ❌ Pro |
| `POST /submissions/pdf` · `docx` · `html` | ❌ Pro |
| `PUT /templates/{id}/documents` | ❌ inexistant en v3.2.3 |

D'où deux modes, interchangeables par configuration :

**`DOCUSEAL_MODE=template`** (défaut, édition libre)
Un gabarit par type de convention est préparé **une fois** dans l'interface
DocuSeal ; l'application n'envoie que les signataires et les valeurs à
préremplir. Les identifiants de gabarit se renseignent dans
`DOCUSEAL_TEMPLATE_EQUITY|DONATION|LOAN|REWARD`.

**`DOCUSEAL_MODE=oneoff`** (édition Pro, 20 $/utilisateur/mois)
Le PDF déjà rempli par `ConventionGenerator` est posté tel quel, emplacements
de signature en coordonnées fractionnaires (0 → 1). Aucun gabarit à maintenir,
et les modèles `.docx` validés juridiquement restent intacts.

### Câbler les gabarits (mode `template`)

```bash
php artisan docuseal:templates
```

Liste les gabarits, leurs rôles et le **nom exact** de chaque champ, en
signalant ceux qui ne correspondent à aucune clé du contexte — un champ mal
nommé ne serait jamais prérempli, sans erreur visible.

Les champs du gabarit doivent porter le nom des clés de
`ConventionContext::build()` :

```
investor_name, investor_address, investor_kyc_ref,
company_name, company_legal_form, company_rccm, company_tax,
company_address, company_representative,
operator, amount_in_words, amount_figures, currency,
payment_means, disposition_date, payout_account,
contract_date, contract_place, jurisdiction_law,
jalon_1_desc, jalon_1_montant, jalon_1_date   (idem 2 et 3)
```

Les rôles des signataires doivent valoir « Investisseur » et « Porteur de
projet » (cf. `config/signature.roles`).

## 3. Mise en service

### 3.1 Corriger l'URL de l'application (indispensable)

*Paramètres → Compte → URL de l'application* affiche
`http://187.124.47.9:32769`. Tous les liens de signature générés par DocuSeal
utilisent cette valeur : ils pointeraient vers une adresse IP en HTTP, non
joignable proprement et non rassurante pour un signataire.

Remplacer par : `https://sign.globalafricaplus.com`

### 3.2 Récupérer le jeton API

*Paramètres → API* → bouton **COPIER** (le jeton commence par `EL2pz…`), puis
sur le VPS dans `shared/.env` :

```
DOCUSEAL_API_TOKEN=<le jeton>
```

### 3.3 Déclarer le webhook

*Paramètres → Webhooks* → URL :

```
https://globalafricaplus.com/api/v1/webhooks/docuseal
```

Événements à cocher : `form.completed`, `form.declined`,
`submission.completed`, `submission.expired`.

`php artisan docuseal:check` affiche l'URL exacte, jeton partagé inclus si
`DOCUSEAL_WEBHOOK_SECRET` est renseigné.

### 3.4 SMTP — ou pas

Le SMTP Hostinger est configuré côté DocuSeal (variables `SMTP_ADDRESS`,
`SMTP_PORT`, `SMTP_USERNAME`, `SMTP_PASSWORD`, `SMTP_FROM`,
`SMTP_ENABLE_STARTTLS` dans le YAML du conteneur ; port 587 en STARTTLS, le nom
d'utilisateur étant l'adresse complète de la boîte).

- `DOCUSEAL_SEND_EMAIL=false` (défaut) — aucun email ; l'application affiche à
  chaque partie **son** lien de signature (bouton « Signer maintenant »).
  Recommandé tant que la recette tourne sur des comptes de test.
- `DOCUSEAL_SEND_EMAIL=true` — DocuSeal envoie lui-même les demandes de
  signature aux adresses des deux parties.

## 4. Sécurité

**Signature HMAC des webhooks.** DocuSeal signe chaque appel :

```
X-Docuseal-Signature: <timestamp>.<hmac_sha256_hex>
```

Le HMAC porte sur la chaîne `"{timestamp}.{corps brut}"`, avec le secret
**complet, préfixe `whsec_` inclus** (Webhooks → SÉCURITÉ → onglet HMAC), et une
tolérance d'horloge de 5 minutes — algorithme relevé dans
`lib/webhook_urls/signatures.rb` du dépôt DocuSeal, pas déduit. La comparaison
se fait en temps constant (`hash_equals`).

**Seconde couche.** Le payload reste un simple déclencheur :
`WebhookController::docuseal()` re-vérifie systématiquement le statut via
`GET /submissions/{id}` avant toute écriture. Même sans secret configuré, un
appel forgé ne peut donc rien valider.

Les liens de signature des **deux** parties sont stockés dans
`investments.signature_sign_urls`, colonne **masquée** des réponses API.
Chaque utilisateur ne reçoit que le sien via l'attribut `my_sign_url` — sans
quoi une partie pourrait signer à la place de l'autre.

## 5. Points restant à traiter

1. **Choix du mode.** En `template` (défaut), les 4 gabarits restent à créer
   dans l'interface et à câbler dans `DOCUSEAL_TEMPLATE_*`. En `oneoff` (Pro),
   rien à préparer mais une licence est requise.
2. **Position des champs de signature** (mode `oneoff` uniquement) :
   `config/docuseal.fields` place les deux blocs en bas de la 1ʳᵉ page. À
   réajuster après relecture des modèles — un champ mal placé recouvrirait du
   texte.
3. **Certificat & horodatage** : passer du certificat auto-généré à un
   certificat qualifié + TSA avant les signatures à valeur probante.
4. **Revue juridique** des 4 modèles de convention (toujours en attente).
